签到巡检（独立于所有签到项目）

【它解决什么】
以前告警代码长在签到任务里面，任务没启动时告警代码也一起没启动，
所以「几天没运行」这种最严重的情况反而一条消息都没有。
本仓库是独立的第三方检查者，每天北京时间 14:07 用 GitHub API
检查五个项目「今天有没有真正跑起来」，发现异常才推企业微信。

【检查范围】
  迅维网        chinafix-sign
  Hyperdown     hyperdown-checkin
  WorkBuddy     workbuddy-checkin-public
  小浣熊        raccoon-checkin
  天翼云盘      Cloud189Checkin

【每天的时间表（北京时间）】
  00:47  天翼云盘 Cloud189Checkin   UTC 16:47   cron 47 16 * * *
  00:58  小浣熊   raccoon-checkin    UTC 16:58   cron 58 16 * * *
  01:09  WorkBuddy                  UTC 17:09   cron 9 17 * * *
  01:21  Hyperdown                  UTC 17:21   cron 21 17 * * *
  01:33  迅维网   chinafix-sign      UTC 17:33   cron 33 17 * * *
  ── 五个项目错峰 11 分钟，都在凌晨 1 点前后，全部避开整点 ──
  14:07  巡检跑一次：项目级告警当场推（UTC 06:07，cron 7 6 * * *）
  15:07  心跳兜底告警：只在「巡检自己没跑」时推（Grace 1 小时）

【判定口径】只查有没有运行，不查业务是否签到成功
  · 今天有成功完成的运行           → 正常，静默
  · 今天正在运行 / 刚排队          → 正常，不误报
  · 今天一次都没运行               → 异常，推送
  · 今天有运行但被拦、失败、排队超时 → 异常，推送
    （action_required / failure / queued 卡住，都是 0 个 job，等于没跑）
  · 签到跑起来了但失败：各项目自己会推，本巡检不重复判断

【推送策略】
  全绿时完全不打扰；有异常才推一条企微，并把本次巡检任务标红，
  GitHub 还会另发一封失败邮件，等于双通道。
  想手动验证推送通道：Actions 页面运行本 workflow，勾选「发一条测试告警」。

【配置】仓库 Secrets
  WATCH_PAT      能读取五个私有仓库 Actions 运行记录的令牌（已配好）
  WECOM_APP      corpid,corpsecret,touser,agentid（已配好）
  HEARTBEAT_URL  可选：第三方心跳服务的 ping 地址，不填就跳过心跳

【外部心跳（可选，兜住「巡检自己没运行」）】
  配好 HEARTBEAT_URL 后，巡检每次真正跑完会向该地址发一次 GET 报平安。
  外部服务设成「每天 UTC 06:07（北京 14:07）应收一次，宽限 1 小时」：
    · 按时收到 → 保持沉默，手机不打扰
    · 北京 15:07 还没收到 → 服务主动把告警推到手机
  全程云端自动：ping 由 GitHub Actions 发出，不需要开电脑、不用人工操作。
  免费服务可用 healthchecks.io（免费 20 个检查、不需要信用卡）；
  任何支持「超时未 ping 告警」的服务都行，这里只认一个 URL，没有绑定。
  注意：心跳只表示「巡检跑过了」，不代表五个项目都签到成功；
  后者仍由本巡检每天 14:07 判定并按需推企微。

【为什么会自动停：三种「停」不是一回事】
  1) 风控挂起（GitHub 2026-07-28 新规）
     表现：run 显示 action_required 或一直 queued，0 个 job、没有任何日志。
     范围：官方公告明确「目前仅适用于 github.com 上的公开仓库」；
           必须有写权限的人在已登录的网页会话里点 Approve，CLI/API 批不了。
     处理：把仓库转成 Private 就不会再中（五个项目已全部转私）。
           所以「已经转私仓，还会被这条拦吗」——不会。
  2) 定时工作流被自动禁用
     表现：Actions 页黄色横幅「...disabled because there hasn't been
           activity in this repository for at least 60 days」。
     范围：GitHub 官方文档写的是「公开仓库 60 天无仓库活动自动禁用」，
           私有仓库不在该条款内；但社区有零星私仓也中的报告，故仍做保活。
     处理：点 Enable workflow 即可。本巡检现在每天额外检查五个项目
           workflow 的 state，发现 disabled_* 会尝试用 API 自动重新启用，
           并把结果写进告警；自动重开失败才需要手动点。
           本仓库自带 keepalive.yml，每月 1 号一次空提交，避免走到 60 天。
  3) 与公私有无关的常见原因
     令牌/Secret 过期、平台改密码导致登录态失效、Actions 额度耗尽、
     cron 高峰期排队、仓库被 archive、默认分支被改。
     这些表现为 failure 或「今天没运行」，按告警里的 5 步速查处理。
  结论：转私仓只解决了第 1 条，不等于「永远不会停」；
        真正兜底的是「巡检 + 自动重开 + 外部心跳」这一套闭环。

【告警里现在会写什么】
  逐条列出异常项目的原因、工作流是否被停用、已经自动做了什么；
  末尾固定附「停了怎么解决」5 步速查（含手动补签入口 Run workflow），
  以及「连巡检消息都没收到时该去哪里点启用」。

【为什么把项目挪到凌晨、把告警提前到下午 2 点】
  改动前的观测（2026-11-07~09，连续三天稳定）：
    五个 cron 名义是 UTC 00:05 / 00:05 / 01:00 / 01:17 / 02:35
    （北京 08:05 / 08:05 / 09:00 / 09:17 / 10:35），
    实际跑完是北京 13:45 / 13:53 / 15:48 / 17:34 / 18:10，
    即统一延迟 5.5~7.5 小时。根因是五个任务全挤在 UTC 00~02
    这个 GitHub 每日调度最拥堵的时段，排队消化要几个小时。

  现在把五个任务错峰挪到 UTC 16:47~17:33（北京 00:47~01:33），
  避开高峰、也避开整点。这个改动是「净赚」，理由不依赖
  「延迟一定会消失」这个未经验证的假设：
    · 最好情况：换时段后不再排队，凌晨 1 点前后就跑完；
    · 最坏情况：仍延迟 7 小时，也会在上午 7:47~8:33 跑完，
                 比原来的 18:10 早约 10 小时。
  两种情况 14:07 巡检都留有余量，所以项目级告警可以放心提前到下午 2 点，
  心跳兜底告警 15:07，白天有充足时间处理。

  仍需观察 2~3 天：如果某个项目实际跑完时间稳定早于上午 10 点，
  巡检还可以再往前提。反过来说，若某天 GitHub 调度异常、14:07 时
  当天 run 还没创建，巡检会误报一次；告警里带处置步骤，
  核对 Actions 页确认在跑或已跑完，忽略即可，也可手动 Run workflow 补跑。
  巡检对「当天已创建但还在排队/运行中」的 run 判正常，不会误报这一类。

【已知边界】
  不配 HEARTBEAT_URL 时，巡检只在异常时推，所以「巡检自己没运行」
  仍需靠人发现：14:07 后打开 .../actions 看一眼有没有当天绿勾。
  配好外部心跳后，这一环才真正闭环。
  自动重新启用需要 WATCH_PAT 带 repo / actions:write 权限；权限不足时
  会在告警里明确提示「请到 Actions 页点 Enable workflow」。
  巡检目前不区分 run 的触发方式，手动 workflow_dispatch 也算「今天运行过」。
  巡检仓库自身至今只跑过手动触发，定时是否准时还需明天首次验证；
  若某天 15:07 收到心跳超时但 14:07 的项目级告警/全绿状态正常，
  说明是巡检自身调度延迟导致的误报，忽略即可。

【路线 ①：外部心跳完整落地（推荐，改动最小）】
  目标：让第三方服务在「巡检自己没运行」时主动推企微，闭掉最后一个死结。
  代码已就绪：watchdog.py 的 ping_heartbeat() 只要检测到 HEARTBEAT_URL，
  巡检每次真正跑完就 GET 一次；没跑就不 ping，服务到点自己告警。

  1) 注册 healthchecks.io（邮箱魔法链接登录，无密码、无需信用卡）
     免费 Hobbyist 给 20 个 check，本方案只用 1 个。
  2) 新建 1 个 check（已建过的直接编辑，改下面两个值即可）
     Name:     签到巡检
     Schedule: Cron，表达式 7 6 * * *  （UTC 06:07 = 北京 14:07）
     Grace:    1 小时                  （北京 15:07 没 ping 才告警）
     Timezone: 保持 UTC，别再手动换算，否则会差 8 小时
     ⚠️ 必须和 watch.yml 里的 cron 完全一致，两边不一致会天天误报。
  3) 复制该 check 的 Ping URL（形如 https://hc-ping.com/xxxxxxxx）
     本仓库 Settings > Secrets and variables > Actions > New repository secret
     名称 HEARTBEAT_URL，值填 Ping URL。不要提交进代码、不要贴聊天。
  4) 加告警通道（建议两个都开，互为冗余）
     a. Email：填常用邮箱，免费、不受境外访问影响。
     b. Webhook -> 本仓库的 repository_dispatch（推荐，不用装企业微信 APP）
        让 Healthchecks 用一次 POST 触发本仓库的 heartbeat_alert job，由它
        用已有的 WECOM_APP 完成「gettoken + message/send」两步，最终推到
        微信里那个叫「东东推送」的自建应用会话 —— 与 14:07 巡检同一条通道，
        已实测可达。Healthchecks 在境外，但目标是 api.github.com，比直连
        qyapi.weixin.qq.com 更稳。

        ⚠️ Healthchecks 的 Webhook 表单里 Method 默认是 GET，此时界面上
        **没有** Request body 输入框（截图里看不到属正常）。先把 Down 和
        Up 两组的 Method 都改成 POST，Request body 才会出现。两组字段都是
        必填，Headers 也要两组各填一次，别只填左边。
        ⚠️ 第二个坑：两个 Request Headers 框里预填了示例文字
          X-Sample-Header: $NAME has gone down / $NAME is back up
        那只是占位示例，必须在框内 Ctrl+A 全选删掉，换成下面 4 行真实
        认证头。留着示例等于没带 Authorization，GitHub 返回 401，
        Healthchecks 判失败并重试 2 次，微信收不到任何消息。

        Down 组：
          Method   POST
          URL      https://api.github.com/repos/caiping527/checkin-watchdog/dispatches
          Request Headers（每行一条，令牌用你自己的 GitHub 令牌）：
            Accept: application/vnd.github+json
            Authorization: Bearer <GitHub 令牌>
            Content-Type: application/json
            X-GitHub-Api-Version: 2022-11-28
          Request Body：
            {"event_type":"heartbeat_down","client_payload":{"name":"$NAME","status":"$STATUS","now":"$NOW"}}

        Up 组（必填，填同一个 URL 和 Headers，只换 event_type）：
          Request Body：
            {"event_type":"heartbeat_up","client_payload":{"name":"$NAME","status":"$STATUS","now":"$NOW"}}

        $NAME / $STATUS / $NOW 由 Healthchecks 自动替换。Up 事件只在真出过
        故障后触发一次，会回一条「已恢复」，方便确认修好了。

        令牌（为什么网页上看不到）：GitHub 的 Personal access token 只在
        创建成功那一刻显示一次，之后网页列表、详情页和任何 API 都取不回
        明文；点进已有的 workbuddy 只能改名 / 改权限 / 删除。想「查看」
        只能 Delete 后重新 Generate，反而多一个新令牌。
        本机 gh CLI 已保存截图里那个 workbuddy classic token
        （scopes: repo, user, workflow），直接复用即可，不用新建：
        本机执行 gh auth token 可取回（值别贴到聊天、别提交 git）。
        2026-11-09 已实测用它带 Bearer 头访问 GitHub API 返回 200。
        注意 classic token 权限覆盖全部仓库，填进 Healthchecks 后由第三方
        保管；若以后想收紧，再建 fine-grained PAT 只勾 checkin-watchdog
        一个仓库、Contents: Read and write，泄漏时可单独吊销。
        repository_dispatch 要求对该仓库有写权限，只读令牌会返回 404。

        配置页有 Test 按钮：点一下会触发一次真实 Down 告警，手机收到即通。
  5) 验证闭环
     · 首次激活（最容易漏）：官方把「从未收到 ping」的 check 标为 New 状态，
       告警只在 check 进入 Down 时发出。所以配好 HEARTBEAT_URL 后，
       务必先手动 Run workflow 一次，让 Last Ping 从 Never 变成当前时间、
       状态变成 Up，这条链路才算真正通电并有基线；在此之前不要指望它兜底。
       检查列表里若一直显示 Last Ping: Never，说明 GitHub Secret 没配、
       或巡检根本没跑到发 ping 那一步，先排查这两处。
     · 正常：北京 14:07 巡检跑完 -> Healthchecks 显示 Up -> 手机不打扰。
     · 模拟故障：临时把 HEARTBEAT_URL 改成错误地址，等 15:07 后看 Email /
       企微有没有告警；验证完改回来。
     · 或在本仓库 Actions 手动 Run workflow 一次，Healthchecks 的 Last Ping
       应立即刷新成当前时间。

  【为什么不用短信】Healthchecks 官方免费版不含 SMS / 电话（要 $20/月
  Business 才给 50 条短信额度）；国内短信本身也有通道费。企业微信自建应用
  消息免费、手机弹通知、国内直达，已经在用，没必要再买短信。

  【为什么不用 Docker 自托管】Uptime Kuma / Healthchecks 自托管版都能跑
  Docker，但 2026 年免费容器平台普遍休眠（Render 15 分钟无访问、Koyeb 1
  小时缩容到零、Fly.io 仅 7 天试用、Railway 每月 $1 额度约够 6 天），监控
  系统自己睡了就失效；自托管还多一个「监控挂了谁报」的死结。只在有常驻
  NAS / 云主机时当第二意见，不要当主链路。

  【凭据格式】WECOM_APP 只读前 4 段：corpid,corpsecret,touser,agentid。
  多出来的第 5 段会被忽略，不要塞进 WECOM_APP。凭据不要贴进聊天、不要
  提交进代码；本次改动没有回显或写死任何凭据。

【心跳告警怎么到手机（最容易搞混的一点）】
  先认清一件事：微信里那个叫「东东推送」的会话，不是独立推送服务，
  就是你自己注册的企业微信自建应用通过「微信插件」在微信里的显示名。
  之前那条「签到巡检异常」测试告警正是它推的，所以这条通道早就通了，
  不需要下载企业微信 APP，也不需要建群、加群机器人。

  为什么不是「群机器人」：群机器人虽然一次 POST 直达（Healthchecks 的
  Webhook 只能发一个请求），但腾讯官方在微信开放社区明确回复「企业微信群
  及其他推送的消息目前不支持同步到微信插件」。也就是说装了 APP 建了群，
  消息大概率只留在企业微信里，微信收不到。第三方教程说可以，是额外在
  管理后台开了「允许成员在微信插件中接收和回复聊天消息」开关，且各端表现
  不一致，不可靠。所以本项目不用它。

  为什么需要绕一下：自建应用要 gettoken + message/send 两步 HTTP，
  Healthchecks 一次请求做不到。解法是让 Healthchecks 把「一次 POST」
  打到 GitHub 的 repository_dispatch，由本仓库的 heartbeat_alert job
  完成剩下的两步。job 与 14:07 巡检共用 WECOM_APP，推到同一个微信会话。
  该 job 不跑巡检、也不发报平安 ping，避免把故障告警误当作巡检正常。

  【完整链路】
  平时：巡检 14:07 跑完 -> GET HEARTBEAT_URL -> Healthchecks 记 Up -> 静默。
  出事：巡检没跑 / 被停用 / GitHub 调度丢失 -> 15:07 没 ping -> Down
        -> Healthchecks POST /dispatches -> heartbeat_alert -> 微信「东东推送」
        -> 同时发 Email（冗余）。

  【这条链路的边界，必须知道】
  Healthchecks 判超时和发通知在 GitHub 外面，所以「巡检仓库自己没跑」能兜住；
  但告警的最后一步借了 GitHub Actions 来发消息。若 GitHub 整体故障到连
  Actions 都起不来，这条告警也会一起失效 —— 此时只有 Email 能到你。
  想彻底不依赖 GitHub，就换成 PushPlus / Server酱 这类一步到微信的通道：
  微信扫码拿 token，Webhook 的 URL 填 https://www.pushplus.plus/send ，
  Down 请求体 {"token":"<你的token>","title":"⚠️ 签到巡检心跳超时",
  "content":"巡检今天没报平安，打开 github.com/caiping527/checkin-watchdog/actions 点 Run workflow",
  "template":"txt","channel":"wechat"}；代价是多注册一个服务。

    必须同时把 Healthchecks check 的 Cron 表达式改成同一个值，两边不一致会天天误报。
  改项目签到时间：各仓库 .github/workflows/ 下的 cron，注意五个项目保持错峰、
    避开整点，并给巡检留出足够余量。
  增删项目：watchdog.py 顶部的 TARGETS 列表
